# Deployment

## Local

- `pnpm install`
- `pnpm dev`
- `docker compose up`

## Production-oriented assets

- Multi-stage Dockerfiles for `services/api` and `services/notification`
- Docker Compose for PostgreSQL, Redis, API, and notification
- GitHub Actions for install, lint, typecheck, build, and Prisma validate
- Coolify-ready container workflows
- Cloudflare-ready edge/static deployment for frontend apps

## Free-tier stack: Vercel + Supabase + Upstash + Render

This path deploys everything on free tiers: `apps/web` and `apps/landing` on
Vercel, PostgreSQL on Supabase, Redis on Upstash, and `services/api` /
`services/notification` on Render (using the existing Dockerfiles). Order
matters because later steps need URLs/secrets from earlier ones.

### 1. Database — Supabase

1. Create a project at supabase.com (free tier).
2. Project Settings → Database → Connection string → select **Session
   pooler** (not the direct connection). Render's network egress is
   IPv4-only and Supabase's direct connection is IPv6-only on the free
   plan, so the pooler is required for connectivity. Copy it as
   `DATABASE_URL` — it looks like:
   `postgresql://postgres.<ref>:<password>@aws-<region>.pooler.supabase.com:5432/postgres`
3. From your machine, run the initial migration against that URL:
   ```bash
   DATABASE_URL="<supabase-session-pooler-url>" pnpm db:deploy
   ```
   Re-run this command any time you add new Prisma migrations.

### 2. Redis — Upstash

1. Create a free Redis database at upstash.com (Render no longer offers a
   free managed Redis).
2. Copy the **TLS** connection string (`rediss://default:<password>@<host>:<port>`)
   — this becomes `REDIS_URL` for both Render services.

### 3. Email — SMTP provider

`SMTP_URL` and `EMAIL_FROM` are required (not optional) by both services.
Mailpit (used in `docker-compose.yml`) is dev-only. Pick a free SMTP
provider (e.g. Resend, Brevo) and set `SMTP_URL` to
`smtp://<user>:<pass>@<host>:<port>`.

### 4. API + notification — Render

1. In Render, **New → Blueprint**, point it at this repo/branch. It will
   read `render.yaml` at the repo root and create two Docker web services:
   `restaurantos-api` and `restaurantos-notification`, both on the free
   plan.
2. Fill in the secrets Render prompts for (marked `sync: false` in
   `render.yaml`): `DATABASE_URL`, `REDIS_URL`, `SMTP_URL`, `EMAIL_FROM`,
   `APP_URL`, `LANDING_URL`, `API_URL`, `CORS_ORIGINS`. `JWT_ACCESS_SECRET`
   / `JWT_REFRESH_SECRET` are auto-generated by Render.
   - `CORS_ORIGINS` needs your future Vercel URLs — set placeholders now
     and update them after step 5 (Render redeploys automatically on env
     var changes).
   - `API_URL` / `APP_URL` can be set once Render assigns
     `restaurantos-api.onrender.com`.
3. Deploy. Note the resulting `restaurantos-api.onrender.com` URL —
   `/api/v1/health` should return `200`.
4. Free-tier services spin down after 15 minutes of inactivity and cold
   start on the next request (a few seconds delay).

### 5. Web + landing — Vercel

`apps/web/vercel.json` and `apps/landing/vercel.json` already set the
correct install/build commands for this pnpm/Turborepo monorepo.

1. In Vercel, **Add New → Project**, import this repo, once per app:
   - Project 1: Root Directory = `apps/web`
   - Project 2: Root Directory = `apps/landing`
   Vercel auto-detects Next.js and picks up each app's `vercel.json`.
2. Set env vars on the `apps/web` project (from `packages/config`'s
   `webEnvSchema`):
   - `NEXT_PUBLIC_API_URL` = `https://restaurantos-api.onrender.com`
   - `NEXT_PUBLIC_APP_URL` = the web project's own Vercel URL
   - `NEXT_PUBLIC_WS_URL` = `https://restaurantos-api.onrender.com`
3. Deploy both projects.

### 6. Close the loop

Back in Render, update `restaurantos-api`'s `CORS_ORIGINS` to the real
Vercel URLs (comma-separated, e.g.
`https://your-web.vercel.app,https://your-landing.vercel.app`) and
`APP_URL`/`LANDING_URL` to match. Render redeploys automatically.

### Notes

- Everything above stays within each provider's free tier, but free-tier
  limits (Render cold starts, Supabase/Upstash storage caps) make this a
  fit for staging/demo use, not high-traffic production.
- Custom domains, if added later, must be reflected in `CORS_ORIGINS` and
  the `NEXT_PUBLIC_*` / `APP_URL` values on both sides.
